## 1. LiveCodeBench 评测侧载 LoRA 没有真正接入 vLLM

### 问题

早期 `LiveCodeBench` 评测可以用 vLLM 跑 base model，但不能等价评测训练出的 LoRA adapter。问题不是 adapter 文件一定坏了，而是评测 runner 当时没有完整表达“我要启用 LoRA，并在 generate 时使用这个 adapter”。

这会造成两类误判：

- 评测跑的是 base model，却被当作 LoRA checkpoint 的效果。
- 传入了 adapter 路径，但 vLLM 初始化和 generation 没有按 LoRA 模式执行。

### 观察

修复前，`LiveCodeBench/lcb_runner/runner/vllm_runner.py` 只构造普通 `LLM`，`generate()` 也没有传 `lora_request`。

修复前代码，来自 `git show adb7fbd^:LiveCodeBench/lcb_runner/runner/vllm_runner.py`：

```python
from vllm import LLM, SamplingParams

self.llm = LLM(
    model=model_tokenizer_path,
    tokenizer=model_tokenizer_path,
    tensor_parallel_size=args.tensor_parallel_size,
    dtype=args.dtype,
    enforce_eager=True,
    disable_custom_all_reduce=True,
    enable_prefix_caching=args.enable_prefix_caching,
    trust_remote_code=args.trust_remote_code,
    gpu_memory_utilization=args.vllm_max_gpu_memory,
)

vllm_outputs = self.llm.generate(remaining_prompts, self.sampling_params)
```

这段代码的问题是：即使外部知道 LoRA 路径，runner 内部也没有 `LoRARequest`，vLLM 不会加载 adapter。

同一时期 parser 也没有 LoRA 参数。修复前 `git show adb7fbd^:LiveCodeBench/lcb_runner/runner/parser.py` 只到 `--vllm_max_gpu_memory`，没有 `--lora_path` 和 `--vllm_max_lora_rank`。

### 修复

当前代码在 `LiveCodeBench/lcb_runner/runner/vllm_runner.py:4` 引入 `LoRARequest`，在 `LiveCodeBench/lcb_runner/runner/vllm_runner.py:17` 到 `LiveCodeBench/lcb_runner/runner/vllm_runner.py:27` 根据 `args.lora_path` 构造 adapter 请求：

```python
from vllm.lora.request import LoRARequest

self.lora_request = None
use_lora = getattr(args, "lora_path", None) is not None
lora_kwargs = {}
if use_lora:
    lora_kwargs["enable_lora"] = True
    lora_kwargs["max_lora_rank"] = args.vllm_max_lora_rank
    self.lora_request = LoRARequest(
        lora_name="adapter",
        lora_int_id=1,
        lora_path=args.lora_path,
    )
```

然后在 `LiveCodeBench/lcb_runner/runner/vllm_runner.py:28` 到 `LiveCodeBench/lcb_runner/runner/vllm_runner.py:39` 初始化 vLLM 时把 LoRA 开关传进去：

```python
self.llm = LLM(
    model=model_tokenizer_path,
    tokenizer=model_tokenizer_path,
    tensor_parallel_size=args.tensor_parallel_size,
    dtype=args.dtype,
    enforce_eager=True,
    disable_custom_all_reduce=True,
    enable_prefix_caching=args.enable_prefix_caching,
    trust_remote_code=args.trust_remote_code,
    gpu_memory_utilization=args.vllm_max_gpu_memory,
    **lora_kwargs,
)
```

最后在 `LiveCodeBench/lcb_runner/runner/vllm_runner.py:65` 到 `LiveCodeBench/lcb_runner/runner/vllm_runner.py:69` 生成时显式传入 adapter：

```python
vllm_outputs = self.llm.generate(
    remaining_prompts,
    self.sampling_params,
    lora_request=self.lora_request,
)
```

parser 侧也补了参数入口，当前在 `LiveCodeBench/lcb_runner/runner/parser.py:146` 到 `LiveCodeBench/lcb_runner/runner/parser.py:156`：

```python
parser.add_argument(
    "--lora_path",
    type=str,
    default=None,
    help="Path to LoRA adapter weights to sideload during inference (vllm only)",
)
parser.add_argument(
    "--vllm_max_lora_rank",
    type=int,
    default=32,
    help="Max LoRA rank for vllm (must match the rank used during training)",
)
```

### 总结

评测侧载的关键不是“路径存在”，而是三件事同时成立：

- vLLM 初始化时 `enable_lora=True`。
- vLLM 知道 `max_lora_rank`。
- 每次 `generate()` 都带上对应的 `LoRARequest`。

如果以后评测结果和训练 checkpoint 对不上，先检查 runner 是否真的走了 LoRA generation，而不是只看 adapter 文件是否存在。

## 2. Qwen3.5 GDN packed mapping 与 LoRA target 不一致

### 问题

`Qwen3.5` 的 GDN 投影在推理里可以用 fused / packed 表达，例如把多个投影视作一个 packed module。但 LoRA 注入要求 adapter 权重挂到真实子模块上。packed 表达对推理友好，不一定对 LoRA target resolution 友好。

典型风险是：框架把 `in_proj_qkvz` 当成一个 LoRA target，但 adapter 实际对应的是拆开的 `in_proj_qkv` 和 `in_proj_z`。这样会导致模块匹配、权重切片或索引逻辑不一致。

### 观察

历史文档引用了上游 `vllm-project/vllm#36976`。该问题的核心不是普通边界检查，而是 LoRA 场景下不应该继续沿用 fused GDN packed mapping。

本仓库里也能看到相同语义。当前 `ms-swift/swift/megatron/model/gpt_bridge.py:1353` 到 `ms-swift/swift/megatron/model/gpt_bridge.py:1360` 明确把 LoRA target 拆成几个子模块：

```python
if lora_A is not None:
    self._peft_target_modules.update({'in_proj_qkv', 'in_proj_z', 'in_proj_b', 'in_proj_a'})
    for key in ['in_proj_qkv', 'in_proj_z', 'in_proj_b', 'in_proj_a']:
        hf_state_dict[f'{key}.lora_A.weight'] = lora_A.clone()
    hf_state_dict['in_proj_qkv.lora_B.weight'] = lora_B[:qkv_dim].clone()
    hf_state_dict['in_proj_z.lora_B.weight'] = lora_B[qkv_dim:qkv_dim + z_dim].clone()
    hf_state_dict['in_proj_b.lora_B.weight'] = lora_B[qkv_dim + z_dim:-a_dim].clone()
    hf_state_dict['in_proj_a.lora_B.weight'] = lora_B[-a_dim:].clone()
```

这说明当前 LoRA 语义更接近“拆开后的真实 target”，而不是一个抽象 fused target。

### 修复

训练期动态注入曾经尝试过更激进的 tensor key 融合。修复前代码来自 `git show 63a0aa1b^:verl/utils/vllm/utils.py`，其中 `_build_qwen35_tensor_variants(...)` 会尝试把 `in_proj_qkv` 和 `in_proj_z` 融成 `in_proj_qkvz`：

```python
if fuse_qkvz and {"in_proj_qkv", "in_proj_z"} <= set(a_map) and {"in_proj_qkv", "in_proj_z"} <= set(b_map):
    if _tensors_equal(a_map["in_proj_qkv"], a_map["in_proj_z"]):
        del updated[f"{prefix}.in_proj_qkv.lora_A.weight"]
        del updated[f"{prefix}.in_proj_z.lora_A.weight"]
        del updated[f"{prefix}.in_proj_qkv.lora_B.weight"]
        del updated[f"{prefix}.in_proj_z.lora_B.weight"]
        updated[f"{prefix}.in_proj_qkvz.lora_A.weight"] = _clone_tensor(a_map["in_proj_qkv"])
        updated[f"{prefix}.in_proj_qkvz.lora_B.weight"] = torch.cat(
            [_clone_tensor(b_map["in_proj_qkv"]), _clone_tensor(b_map["in_proj_z"])], dim=0
        )
```

这类逻辑的问题是：它把 adapter 权重改写到 fused target 上，可能和 vLLM 当前实际支持的 LoRA modules 不一致。即使某次能绕过报错，也容易牺牲原始模块语义。

当前代码改为保守 key variant，不再融合 `in_proj_*`。在 `verl/verl/utils/vllm/utils.py:53` 到 `verl/verl/utils/vllm/utils.py:94`，只做少量前缀重写和 `out_proj -> proj` 别名候选：

```python
def _build_qwen35_tensor_variants(tensors: dict[str, object]) -> list[tuple[str, dict[str, object]]]:
    variants: list[tuple[str, dict[str, object]]] = [("normalized", tensors)]
    candidates = [
        (
            "collapse_model_prefix",
            _remap_tensor_keys(
                tensors,
                replacements=[("base_model.model.model.language_model.", "base_model.model.language_model.")],
            ),
        ),
        (
            "language_model_model_prefix",
            _remap_tensor_keys(
                tensors,
                replacements=[("base_model.model.model.language_model.", "base_model.model.language_model.model.")],
            ),
        ),
        ...
    ]
```

### 总结

`Qwen3.5 + LoRA` 不能只按普通 linear layer 直觉处理。遇到 LoRA 加载异常时，应检查 target module 和 packed mapping 是否符合模型真实结构。更稳的方向是保留真实子模块名，少做融合改写。

## 3. DAPO 训练期 vLLM LoRA 动态注入失败

### 问题

DAPO 训练时，rollout 侧不能简单从磁盘读固定 adapter；它需要在每个更新阶段拿到 actor 当前 LoRA tensor，并动态注入到 vLLM。`LiveCodeBench/run.sh` 能加载同一份 LoRA，只能证明磁盘侧载可用，不能证明训练期 tensor 注入可用。

失败时典型现象是：actor 侧已经收集到 tensor，vLLM 侧却没有解析出 LoRA layer，最终在 LoRA manager 内部走到空 iterator 或类似 `StopIteration`。

### 观察

训练期动态注入有两段容易出错：

- tensor key 进入 vLLM 后必须能被 `from_lora_tensors()` 解析。
- 多 rollout replica / TP worker 下，每个需要生成的 vLLM worker 都必须加载同一份 adapter。

旧文档里提过“空 tensor worker 跳过 add_lora”，但那只是中间修复。当前代码已经把空 payload 视为错误，因为跳过会导致某些 replica 在生成时实际没有 LoRA。

更具体地看，`ngpus=2` 且 `tensor_model_parallel_size=1` 时，VERL 会形成两个 rollout replica，而不是一个 2 卡 TP replica。当前 `ServerAdapter.__init__` 里 replica 的划分逻辑在 `verl/verl/workers/rollout/vllm_rollout/vllm_rollout.py:110` 到 `verl/verl/workers/rollout/vllm_rollout/vllm_rollout.py:122`：

```python
rank = int(os.environ["RANK"])
local_world_size = int(os.environ["RAY_LOCAL_WORLD_SIZE"])
rollout_world_size = (
    self.config.tensor_model_parallel_size
    * self.config.data_parallel_size
    * self.config.pipeline_model_parallel_size
)
if replica_rank == -1:
    self.replica_rank = rank // rollout_world_size
else:
    self.replica_rank = replica_rank
self.rollout_rank = rank % rollout_world_size
self.node_rank = self.rollout_rank // local_world_size
```

如果 `tp=1`、`data_parallel_size=1`、`pipeline_model_parallel_size=1`，那么 `rollout_world_size=1`：

- rank 0：`replica_rank=0`，`rollout_rank=0`，对应 `vllm_server_0_0`。
- rank 1：`replica_rank=1`，`rollout_rank=0`，对应 `vllm_server_1_0`。

也就是说，两个 rank 都是各自 replica 的 rank0，都会执行 rollout 更新。`_execute_method(...)` 在 `verl/verl/workers/rollout/vllm_rollout/vllm_rollout.py:162` 到 `verl/verl/workers/rollout/vllm_rollout/vllm_rollout.py:170` 只会跳过 `rollout_rank != 0` 的进程；这里两个 rank 的 `rollout_rank` 都是 0，所以都会向自己的 vLLM server 发更新：

```python
if self.rollout_rank != 0:
    return None

if self.server_handle is None:
    self.server_handle = ray.get_actor(f"vllm_server_{self.replica_rank}_{self.node_rank}")

future = self.server_handle.collective_rpc.remote(method, timeout=timeout, args=args, kwargs=kwargs)
```

这解释了为什么问题表现为“一个 rank 加载成功，另一个 rank 失败”：它们不是同一个 vLLM engine 的两个 TP shard，而是两个独立 rollout replica。只要其中一个 replica 没有收到 LoRA adapter，它就会独立退化或失败。

还要注意，这里不能简单说“原版 VERL 不鲁棒”。更合理的理解是：上游优秀开源仓库通常假设权重同步要么走完整参数同步，要么走经过验证的 checkpoint / bucket transfer / merge-LoRA 路径；而我们本地为了支持“训练期不 merge、只动态注入 LoRA tensor”的改动，引入了新的 adapter-only 快路径。这个快路径绕过了原来更通用的权重同步假设，所以需要额外保证跨 replica 的 LoRA payload 一致。

当前本地路径在 `verl/verl/workers/engine_workers.py:690` 到 `verl/verl/workers/engine_workers.py:711` 明确分成两次：

```python
per_tensor_param, peft_config = self.actor.engine.get_per_tensor_param(
    layered_summon=self.layered_summon, base_sync_done=True
)

do_lora_base_sync = False
if not self.peft_merge and peft_config is not None:
    self.rollout.sleep_level = 1
    do_lora_base_sync = not self.base_sync_done

if do_lora_base_sync:
    per_tensor_param_base, peft_config = self.actor.engine.get_per_tensor_param(
        layered_summon=self.layered_summon, base_sync_done=False
    )
    await self.rollout.update_weights(
        per_tensor_param_base, peft_config=peft_config, base_sync_done=False, global_steps=global_steps
    )

await self.rollout.update_weights(
    per_tensor_param, peft_config=peft_config, base_sync_done=True, global_steps=global_steps
)
```

其中 `base_sync_done=True` 表示后一次只同步 LoRA adapter。actor 侧在 `verl/verl/workers/engine/fsdp/transformer_impl.py:837` 到 `verl/verl/workers/engine/fsdp/transformer_impl.py:845` 收集 LoRA：

```python
peft_model = getattr(self.module, "_fsdp_wrapped_module", self.module)
if hasattr(peft_model, "peft_config"):  # LoRA
    if not merge_lora:
        peft_config = peft_model.peft_config.get("default", None)
        params = collect_lora_params(
            module=self.module,
            layered_summon=layered_summon,
            base_sync_done=base_sync_done,
        )
```

这次报错已经证明了问题存在：至少有一个 rank / replica 在 LoRA 更新阶段拿到的是空 LoRA tensors。这个报错发生在生成前的 `checkpoint_manager.update_weights()` / rollout `update_weights()` 链路里，因此根因是多 replica / 多卡 LoRA 同步链路，而不是 Weave 展示问题。

准确地说，这个 bug 是我们本地 LoRA 保存/同步改动引入的副作用。为了让 LoRA 不 merge 到 base model、只保存和同步 adapter，从而减少 checkpoint 体积和权重同步开销，我们引入了非 merge 的 LoRA adapter-only 路径。但这个路径改变了上游原本的同步假设：原来的完整权重同步天然会覆盖每个 rollout replica，而 adapter-only 路径变成了“每个 rank 先本地收集 LoRA，再发给自己对应的 vLLM replica”。

修复前 `collect_lora_params(...)` 在某个 rank 上返回非空、另一个 rank 上返回空，而 rollout adapter-only 路径没有把非空 LoRA payload 广播给所有 replica。因此，节省 LoRA 保存空间的非 merge 设计，和 `ngpus=2, tp=1` 下多 rollout replica 的同步方式发生了冲突：

- LoRA adapter-only 快路径只取 `get_peft_model_state_dict(peft_model)`，目标是只拿 adapter，而不是同步完整 base 参数。
- 本地引入了 `base_sync_done=True` 的非 merge LoRA 同步分支，使 LoRA 不再通过标准 full weight bucket 路径自然覆盖所有 replica。
- 在 `ngpus=2, tp=1` 时，每个 rank 对应一个独立 vLLM replica；旧代码要求每个 rank 本地都独立拿到完整 adapter，然后各自发给自己的 replica。
- 实际日志证明这个要求不成立：一个 rank 拿到非空 LoRA tensors，另一个 rank 拿到空 LoRA tensors。

因此，当 rank0 收集到 372 个 LoRA tensor、rank1 收集到 0 个 LoRA tensor 时，旧代码的行为就是：

1. rank0 序列化非空 payload，发给 `vllm_server_0_0`，replica 0 加载 LoRA 成功。
2. rank1 序列化空 payload，发给 `vllm_server_1_0`。
3. 旧 `utils.py` 遇到空 weights 直接 `return`，replica 1 没有加载 LoRA。
4. 旧 generation 代码发现 adapter 未加载时不抛错，只是不传 `LoRARequest`，于是 replica 1 静默使用 base model。

这才是“一个 rank 成功、另一个 rank 失败”的完整机制。

### 修复

第一部分是 tensor key 规范化和解析。

当前 `verl/verl/utils/vllm/utils.py:165` 到 `verl/verl/utils/vllm/utils.py:201` 对 `TensorLoRARequest` 做处理：

```python
if isinstance(lora_request, TensorLoRARequest):
    # PEFT keys have adapter name between lora_A/lora_B and weight:
    # e.g. "...lora_A.default.weight" -> "...lora_A.weight"
    normalized = {}
    for key, tensor in lora_tensors.items():
        new_key = re.sub(r"\.(lora_A|lora_B)\.[^.]+\.(weight)$", r".\1.\2", key)
        normalized[new_key] = tensor
    lora = None
    last_error = None
    variant_errors: list[str] = []
    for variant_tag, candidate_tensors in _build_qwen35_tensor_variants(normalized):
        try:
            candidate = self._lora_model_cls.from_lora_tensors(
                tensors=candidate_tensors,
                **lora_request_kwargs,
            )
            parsed_layers = len(getattr(candidate, "loras", {}))
            if parsed_layers > 0:
                lora = candidate
                break
        except Exception as e:
            last_error = e
            variant_errors.append(f"{variant_tag}:{type(e).__name__}:{e}")
```

这里解决的是 PEFT adapter 名导致的 key mismatch，以及不同后端前缀差异。关键判断是 `parsed_layers > 0`；如果所有 variant 都解析不出 layer，就在 `verl/verl/utils/vllm/utils.py:188` 到 `verl/verl/utils/vllm/utils.py:201` 打印失败上下文并抛错，而不是继续生成。

第二部分是 LoRA payload 广播。

修复前，`git show 78be41e0^:verl/workers/rollout/vllm_rollout/vllm_rollout.py` 中只在当前 rank 收集并序列化 LoRA：

```python

    lora_weights: dict[str, torch.Tensor] = {}
    async for name, weight in ensure_async_iterator(weights):
        cpu_weight = weight.detach().cpu() if weight.device.type != "cpu" else weight.detach()
        lora_weights[name] = cpu_weight
    serialized_lora_payload = _serialize_lora_payload(lora_weights)

    await self._execute_method(
        "update_lora_weights",
        kwargs={"payload": serialized_lora_payload, "peft_config": peft_config},
    )
```

这段代码的问题是：它默认每个 rank 本地收集到的 payload 都可直接发给自己的 vLLM replica。实际报错证明这个默认不成立：某个 rank 收集到空 payload，于是旧逻辑会把空 payload 发给对应 vLLM worker，导致不同 replica 的 adapter 状态不一致。

当前代码在 `verl/verl/workers/rollout/vllm_rollout/vllm_rollout.py:59` 到 `verl/verl/workers/rollout/vllm_rollout/vllm_rollout.py:81` 新增 `_broadcast_lora_payload(...)`：

```python
def _broadcast_lora_payload(payload: bytes) -> bytes:
    """Share the non-empty LoRA payload collected by one rank with every rollout replica."""
    if not torch.distributed.is_available() or not torch.distributed.is_initialized():
        if not payload:
            raise RuntimeError("Cannot update vLLM LoRA adapter: received no LoRA tensors.")
        return payload

    world_size = torch.distributed.get_world_size()
    if world_size == 1:
        if not payload:
            raise RuntimeError("Cannot update vLLM LoRA adapter: received no LoRA tensors.")
        return payload

    local_size = len(payload) if payload else 0
    payload_sizes = [0 for _ in range(world_size)]
    torch.distributed.all_gather_object(payload_sizes, local_size)
    src_rank = next((rank for rank, size in enumerate(payload_sizes) if size > 0), None)
    if src_rank is None:
        raise RuntimeError("Cannot update vLLM LoRA adapter: no rank collected LoRA tensors.")

    objects = [payload if torch.distributed.get_rank() == src_rank else None]
    torch.distributed.broadcast_object_list(objects, src=src_rank)
    return objects[0]
```

并在 `verl/verl/workers/rollout/vllm_rollout/vllm_rollout.py:195` 到 `verl/verl/workers/rollout/vllm_rollout/vllm_rollout.py:205` 使用它：

```python
if peft_config and base_sync_done:
    lora_weights: dict[str, torch.Tensor] = {}
    async for name, weight in ensure_async_iterator(weights):
        cpu_weight = weight.detach().cpu() if weight.device.type != "cpu" else weight.detach()
        lora_weights[name] = cpu_weight
    serialized_lora_payload = _serialize_lora_payload(lora_weights)
    serialized_lora_payload = _broadcast_lora_payload(serialized_lora_payload)

    await self._execute_method(
        "update_lora_weights",
        kwargs={"payload": serialized_lora_payload, "peft_config": peft_config},
    )
```

这个修复的关键点是：先在训练 rank 间找出任意一个非空 LoRA payload 的 rank，然后把这份 payload 广播给所有 rank / rollout replica。这样 `ngpus=2, tp=1` 时，两个独立 vLLM replica 都会收到同一份 LoRA adapter，不会再出现一个 replica 有 LoRA、另一个 replica 为空的状态。

第三部分是空 payload 和未加载 adapter 不再静默通过。

修复前，`git show 7f6273f0^:verl/workers/rollout/vllm_rollout/utils.py` 会跳过空 tensor：

## 4. Qwen3.5 remove-padding 下 3D position_ids 被切坏

### 问题

`Qwen3.5` 多模态模型使用多轴 `position_ids`。在 `use_remove_padding=true` 时，VERL 会把输入转成 NestedTensor / jagged 形式；当 `ppo_micro_batch_size_per_gpu > 1` 时，micro-batch 切分和重建容易把 3D `position_ids` 的 batch 维、axis 维、seq 维解释错。

典型报错落在 Qwen3.5 rotary embedding 路径，例如维度 3 和 batch size 对不上，或 total token 数和 expected sequence 维对不上。

### 观察

修复前有两个关键错误点。

第一，padding 阶段直接把多轴 `position_ids` 放进通用 jagged NestedTensor。来自 `git show 1fbb848b^:verl/workers/utils/padding.py`：

```python
position_ids_list = []
for i in range(attention_mask.shape[0]):
    curr_mask = attention_mask[i].bool()
    curr_pos_ids = position_ids[i]
    if curr_pos_ids.dim() == 1:  # (seq_len,)
        valid_ids = curr_pos_ids[curr_mask]
    else:  # (4, seq_len)
        valid_ids = curr_pos_ids[:, curr_mask]
    position_ids_list.append(valid_ids)
position_ids_nested = torch.nested.as_nested_tensor(position_ids_list, layout=torch.jagged)
```

这段代码对 2D per-sample tensor `(axes, seq_len)` 不够安全。通用 `as_nested_tensor` 可能把 axis 维当成 ragged 相关维度，后续 micro-batch 切分时更容易被重建错。

第二，FSDP remove-padding forward 曾经直接使用 `.values()`。来自 `git show 1fbb848b^:verl/workers/engine/fsdp/transformer_impl.py`：

```python
if pad_mode == DatasetPadMode.NO_PADDING:
    input_ids_rmpad = input_ids.values().unsqueeze(0)  # (1, total_nnz)
    if position_ids.dim() == 3:
        position_ids_rmpad = position_ids.values().unsqueeze(1)  # (4, 1, total_nnz)
    else:
        position_ids_rmpad = position_ids.values().unsqueeze(0)  # (1, total_nnz)
```

这段代码的问题是：NestedTensor 的 `.values()` 是内部存储布局，不保证等价于模型期望的逻辑布局 `(axes, total_tokens)`。对多轴 position ids 来说，这会把 Qwen3.5 RoPE 所需的轴顺序打乱。

### 修复

最终方案是：RLHF remove-padding 路径里，多轴 `position_ids` 先保持 dense，等进入模型前再按真实 `seq_len` flatten。

当前 `verl/verl/workers/utils/padding.py:58` 到 `verl/verl/workers/utils/padding.py:75` 不再对多轴 position ids 使用 3D jagged，而是 pad 后 stack：

```python
position_ids_list = []
for i in range(attention_mask.shape[0]):
    curr_mask = attention_mask[i].bool()
    curr_pos_ids = position_ids[i]
    if curr_pos_ids.dim() == 1:  # (seq_len,)
        valid_ids = curr_pos_ids[curr_mask]
    else:  # (4, seq_len)
        valid_ids = curr_pos_ids[:, curr_mask]
    position_ids_list.append(valid_ids)
if position_ids_list[0].dim() >= 2:
    # Keep multi-axis position_ids as a dense tensor to avoid repeated
    # rebuilds of 3D jagged NestedTensors during dynamic micro-batching.
    max_position_len = max(pos_ids.shape[-1] for pos_ids in position_ids_list)
    position_ids_nested = torch.stack(
        [F.pad(pos_ids, (0, max_position_len - pos_ids.shape[-1])) for pos_ids in position_ids_list], dim=0
    )
else:
    position_ids_nested = torch.nested.as_nested_tensor(position_ids_list, layout=torch.jagged)
```

当前 `verl/verl/utils/tensordict_utils.py:198` 到 `verl/verl/utils/tensordict_utils.py:218` 新增的 helper 同时支持 dense 和 nested 输入，并按 `seq_lengths` 重建逻辑顺序：

```python
def flatten_3d_nested_position_ids(position_ids: torch.Tensor, seq_lengths: torch.Tensor) -> torch.Tensor:
    """Flatten multi-axis position_ids into (num_axes, total_tokens)."""
    assert position_ids.dim() == 3, f"Expected a 3D tensor for position_ids, got dim={position_ids.dim()}"
    assert seq_lengths.dim() == 1, f"seq_lengths must be 1D, got shape {seq_lengths.shape}"
    if position_ids.is_nested:
        dense_position_ids = torch.nested.to_padded_tensor(position_ids, padding=0)
    else:
        dense_position_ids = position_ids
    position_ids_per_sample = []
    for sample_idx, seq_len in enumerate(seq_lengths.tolist()):
        position_ids_per_sample.append(dense_position_ids[sample_idx, :, :seq_len])

    assert len(position_ids_per_sample) > 0, "position_ids must contain at least one sample"
    return torch.cat(position_ids_per_sample, dim=-1)
```

FSDP 路径在 `verl/verl/workers/engine/fsdp/transformer_impl.py:985` 到 `verl/verl/workers/engine/fsdp/transformer_impl.py:993` 使用该 helper，而不是直接 `.values()`：

```python

    input_ids_rmpad = input_ids.values().unsqueeze(0)  # (1, total_nnz)
    if position_ids.dim() == 3:
        seq_lengths = input_ids.offsets().diff()
        flat_position_ids = tu.flatten_3d_nested_position_ids(position_ids, seq_lengths=seq_lengths)
        _maybe_log_position_ids_debug(position_ids, flat_position_ids, seq_lengths, debug_position_ids)
        position_ids_rmpad = flat_position_ids.unsqueeze(1)
    else:
        position_ids_rmpad = position_ids.values().unsqueeze(0)  # (1, total_nnz)
```

对仍需要 3D jagged 的路径，当前 `verl/verl/utils/tensordict_utils.py:221` 到 `verl/verl/utils/tensordict_utils.py:242` 通过 `nested_3d_position_ids_from_list(...)` 显式把 ragged 维设为最后一维：

```python
position_values = torch.cat(position_ids_list, dim=-1)
...
position_ids_nested = torch.nested.nested_tensor_from_jagged(position_values, offsets=position_offsets)
position_ids_nested._ragged_idx = 2
return position_ids_nested
```

### 总结

这个 bug 的核心不是 Qwen3.5 不能训练，而是多轴 `position_ids` 不能直接套普通 jagged tensor 处理。修复原则是：

- 多轴 position ids 尽量保持 dense；
- remove-padding 时按真实 `seq_len` 拼接；
- 不直接依赖 `.values()` 代表逻辑布局；
- 如果必须构造 3D jagged，显式指定 `_ragged_idx = 2`。

## 5. 显存预算和 batch 参数非常敏感

### 问题

`Qwen3.5 + vLLM + LoRA + DAPO rollout` 组合下，显存预算非常紧。很多配置在逻辑上没错，但会在 vLLM 初始化、wake up、rollout 生成或 actor update 阶段 OOM。

### 观察

这类问题通常不是一个 Python bug，而是配置组合超过资源边界。当前配置里能看到多处保守设置。

例如 `scripts/dapo/config/dapo_qwen3_5_0_8b.yaml:21` 使用较小的 `train_batch_size`，`scripts/dapo/config/dapo_qwen3_5_0_8b.yaml:85` 设置 actor micro batch，`scripts/dapo/config/dapo_qwen3_5_0_8b.yaml:125` 设置 vLLM 显存比例，`scripts/dapo/config/dapo_qwen3_5_0_8b.yaml:127` 限制 `max_num_seqs`：

```yaml
train_batch_size: 8
...
ppo_micro_batch_size_per_gpu: 2
...
gpu_memory_utilization: 0.25
...
max_num_seqs: 16
```

9B raw 配置更保守。`scripts/dapo/config/dapo_qwen3_5_9b_raw.yaml:85` 将 `ppo_micro_batch_size_per_gpu` 固定为 1，`scripts/dapo/config/dapo_qwen3_5_9b_raw.yaml:126` 到 `scripts/dapo/config/dapo_qwen3_5_9b_raw.yaml:128` 限制 vLLM 资源：

```yaml
ppo_micro_batch_size_per_gpu: 1 # force 1 to not fault
...
gpu_memory_utilization: 0.8
max_num_seqs: 16  # 并行序列数，限制在一定范围内以避免显存不足
```

### 修复

这里没有一个单点“代码修复”。实际修复方式是把资源约束显式进入配置和文档：

- 降低 vLLM `gpu_memory_utilization`，避免 rollout worker 把显存吃满。
- 限制 `max_num_seqs`，控制 vLLM 同时调度的序列数。
- 用 `ppo_micro_batch_size_per_gpu` 限制 actor/ref 前向和反向 chunk。
- 在 README 中解释 `gen_batch_size` 和 `train_batch_size` 的真实含义，避免把 prompt batch 误认为 per-device batch。相关说明在 `README.md:71` 到 `README.md:123`。

### 总结

这类问题不能只问“代码有没有 bug”，还要问“这个配置在当前机器上是否可行”。后续调整训练吞吐时，优先按下面顺序排查：

1. rollout 显存：`gpu_memory_utilization`、`max_num_seqs`、response length。
2. actor/ref 显存：micro batch、dynamic batch、token 上限。
3. DAPO batch 语义：`gen_batch_size` 和 `train_batch_size` 是否被误解。

## 6. 代码执行器和 sandbox 难以一次性做稳

### 问题

代码任务的 reward 和数据构造需要执行模型生成的代码。早期尝试过 sandbox、多线程或多进程调度，但真实环境里隔离性、吞吐和稳定性很难同时满足。

### 观察

修复前，`data/code_excutor.py` 的 `_run_cases(...)` 支持并发调度。来自 `git show f91f5ce -- data/code_excutor.py` 的删除片段：

```python
if not use_multiprocessing or len(cases) <= 1:
    return {
        case.index: self.validator.run_case(
            code=code,
            case_input=case.input_data,
            mode=run_mode,
            fn_name=fn_name,
        )
        for case in cases
    }

resolved_workers = max_workers or min(len(cases), (os.cpu_count() or 8))
...
with concurrent.futures.ThreadPoolExecutor(max_workers=resolved_workers) as executor:
    future_to_index = {
        executor.submit(_thread_task, case): case.index for case in cases
    }
```

这段逻辑的问题是：每个 testcase 本身已经会启动隔离 subprocess，再外层并发调度会放大环境差异、资源竞争和错误归因复杂度。某些环境下并发更快，但不一定更稳。

另一个实际问题是模型代码可能调用 `exit()`。如果把 `SystemExit` 一律当作框架崩溃，会误判一部分 stdio 风格代码。当前 `data/code_excutor.py:244` 到 `data/code_excutor.py:266` 在 stdio 执行时捕获 `SystemExit` 并返回已收集 stdout：

```python
try:
    sys.stdin = fake_stdin
    sys.stdout = fake_stdout
    exec(code, namespace)
    return {"ok": True, "actual": fake_stdout.getvalue()}
except SystemExit:
    # 如果代码调用了 exit()，会抛出 SystemExit 异常跳到这里。
    # 在竞赛题中，这通常意味着程序想提前结束并输出结果。
    return {"ok": True, "actual": fake_stdout.getvalue()}
except Exception as exc:
    return {"ok": False, "error_code": "RUNTIME_ERROR", "error_message": repr(exc)}
finally:
    sys.stdin = old_stdin
    sys.stdout = old_stdout
```

### 修复

当前 `_run_cases(...)` 已经变成单线程顺序执行。落点在 `data/code_excutor.py:510` 到 `data/code_excutor.py:522`：

```python
def _run_cases(
    self,
    code: str,
    cases: Sequence[NormalizedTestCase],
    run_mode: str,
    fn_name: Optional[str],
) -> Dict[int, Dict[str, Any]]:
    return {
        case.index: self.validator.run_case(
            code=code,
            case_input=case.input_data,
            mode=run_mode,
            fn_name=fn_name,
        )
        for case in cases
    }
```

当前 `data/code_excutor.py:290` 到 `data/code_excutor.py:309` 也对 `TimeoutError`、`SyntaxError`、普通 `Exception` 和 `BaseException` 分层归因：

```python
try:
    if mode == "call_based":
        exec(code, namespace)
        result = _run_call_based(namespace, fn_name, case_input)
    else:
        compile(code, "<generated>", "exec")
        result = _run_stdio(namespace, code, case_input)
except TimeoutError as exc:
    result = {"ok": False, "error_code": "TLE", "error_message": repr(exc)}
except SyntaxError as exc:
    result = {"ok": False, "error_code": "COMPILE_ERROR", "error_message": repr(exc)}
except Exception as exc:
    result = {"ok": False, "error_code": "RUNTIME_ERROR", "error_message": repr(exc)}
except BaseException as exc: # 拦截 SystemExit, KeyboardInterrupt 等
    if isinstance(exc, SystemExit):
        result = {"ok": False, "error_code": "RUNTIME_ERROR", "error_message": "Code attempted to exit() prematurely."}
    else:
        result = {"ok": False, "error_code": "RUNTIME_ERROR", "error_message": f"Critical Error: {repr(exc)}"}
```

### 总结

执行器是训练系统的一部分，不是一个独立小工具。这里的取舍是：优先稳定和可归因，再考虑并发吞吐。后续如果重新引入 sandbox 或并发执行，应该先验证：

- 每个 testcase 的错误是否仍能准确归因；
- timeout 和 memory limit 是否仍然生效；
- 外层并发是否会放大 subprocess 资源竞争；
- reward 统计是否会因为执行器不稳定而失真。

---

## 最终结论

这些问题不是孤立 bug，而是三类工程假设失效：

- 训练和评测不是同一条 LoRA 路径：磁盘侧载成功，不代表训练期 tensor 动态注入成功。
- Qwen3.5 不是普通 text-only dense 模型：GDN target mapping 和 3D `position_ids` 都需要特殊处理。
- 资源和执行环境是一等约束：显存、batch、sandbox、并发都会改变系统是否真正可用。

后续排查类似问题时，优先回答四个问题：

1. 当前失败发生在训练、rollout、评测还是执行器？
2. 失败路径用的是磁盘 adapter、内存 tensor，还是跨 worker payload？
3. 当前模型结构是否需要特殊 target mapping 或 position ids 处理？
4. 当前参数组合是否已经超过显存、并发或执行器稳定边界？
